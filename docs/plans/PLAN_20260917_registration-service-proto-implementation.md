# Objective

Create the `RegistrationService` proto files in `proto/fjarm/registration/v1/` based on the approved draft in `registration.md`. Drop "User" from RPC/message names, remove `UserHandle` from the flow (handles will be autogenerated server-side), and align with existing project conventions.

## Design decisions

1. **Drop "User" prefix** from all RPC and message names → `BeginRegistration`, `CompleteRegistration`, `RefreshRegistrationToken`.
2. **Remove `UserHandle`** from `RegistrationCredentials` — handle is autogenerated server-side and editable later via `UpdateUser`.
3. **`RegistrationCredentials`** contains only `UserEmailAddress` + `UserPassword` (imports from `fjarm.users.v1`).
4. **Inline idempotency key** as a `string` field with UUID validation, matching `CreateSessionRequest` and `CreateUserRequest`.
5. **`CompleteRegistrationRequest`** sends back the `registration_token` string + the `idempotency_key`. The server validates the token, and if valid, internally calls `CreateUser`.
6. **`CompleteRegistrationResponse`** is empty — mirrors `CreateUserResponse` to prevent account enumeration.
7. **`RefreshRegistrationTokenRequest`** requires the email address (to look up the pending registration) + an idempotency key.

## [Update: 2026-09-17 23:38] - Drop RefreshRegistrationToken RPC

* **Context**: The `RefreshRegistrationToken` RPC adds complexity without meaningful UX benefit. A `RegistrationToken` should have a short TTL (~5 minutes) — sufficient for a two-step form. If the token expires, the user restarts registration (re-entering email + password is trivial). Dropping the refresh endpoint also eliminates a potential email enumeration vector.
* **Objective**: Reduce the service to 2 RPCs: `BeginRegistration` and `CompleteRegistration`.
* **Changes to Tasks**:
  - **Removed**: `refresh_registration_token_request.proto` and `refresh_registration_token_response.proto` — no longer needed.
  - **Removed**: Design decision #7 (`RefreshRegistrationTokenRequest` requires email).
  - **Modified**: `registration_service.proto` now defines 2 RPCs instead of 3.

## [Update: 2026-09-17 23:48] - Email-based token delivery

* **Context**: The `RegistrationToken` should be delivered to the user via email, not returned in the `BeginRegistrationResponse`. This turns registration into an email verification flow: client submits credentials → server emails a token → client submits the token to complete registration.
* **Objective**: Adjust message designs to reflect that the token is never exposed in API responses.
* **Changes to Tasks**:
  - **Modified**: `BeginRegistrationResponse` is now an empty acknowledgment (like `CompleteRegistrationResponse`).
  - **Modified**: `RegistrationToken` simplified to a string wrapper (like `AccessToken`). The `expires_at` field is removed — token expiry is a server-side concern, not part of the API contract.
  - **Modified**: `CompleteRegistrationRequest` now includes a `RegistrationToken` field (the token the user received via email) in addition to the `idempotency_key`.
  - **Removed**: `registration_token.proto` no longer imports `google/protobuf/timestamp.proto`.
* **Revised Message Designs**:

  | Message | Fields |
  |---|---|
  | `RegistrationCredentials` | `email_address` (UserEmailAddress) + `password` (UserPassword) |
  | `RegistrationToken` | `registration_token` (string, required, min_len=1) |
  | `BeginRegistrationRequest` | `idempotency_key` (string, required, uuid) + `registration_credentials` (RegistrationCredentials, required) |
  | `BeginRegistrationResponse` | *(empty)* |
  | `CompleteRegistrationRequest` | `idempotency_key` (string, required, uuid) + `registration_token` (RegistrationToken, required) |
  | `CompleteRegistrationResponse` | *(empty)* |
